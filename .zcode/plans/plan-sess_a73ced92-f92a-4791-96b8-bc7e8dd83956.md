# تنفيذ Production Readiness Loop — إعادة إثبات كاملة ثم إصلاح ثم تحقق

## الإطار المعتمد (حسب رسالتك)
الخطة السابقة = إطار عمل فقط، وليست مصدر حقائق. كل Finding يُعاد إثباته من الحالة الحالية (كود/SQL/CI/tests/DB) قبل اعتماده. CURRENT CODE/CURRENT DATABASE/CURRENT CI يحسم أي تعارض.

## Phase 0 — DISCOVER (إعادة إثبات الأساس)
1. git state لكلا المستودعين: fetch origin main، HEADs، حالة التتبع الفعلية للأسرار (`git ls-files` عن db_url*، keystore، key.properties، google-services.json، .env*).
2. Toolchain: flutter/dart/node/pnpm/supabase/docker/openssl — ما لا يتوفر = UNVERIFIED مع الدليل المطلوب.
3. شهادات pinning: تواريخ الانتهاء بـ openssl (إعادة إثبات، لا اعتماد للتقرير القديم).
4. Live DB ground truth (قراءة فقط، صفر تعديل): أي من `check_student_app_access`/`check_user_access` موجود فعلًا في pg_proc، وهل يوجد Realtime publication لجدول users.
5. Baseline قابل للقياس: `flutter pub get` → build_runner → `flutter analyze` → `flutter test`.

## Phase 1 — CONFIRM/THINK ثم IMPLEMENT للـ P0
1. تعارض شجرتي schema (يُعاد إثباته بالـ diff الفعلي ثم بـ ground truth من DB) → توحيد الشجرة المرجعية مع الحفاظ على عمل طرفي التطبيق والـ Dashboard، بترتيب config.toml، والتحقق على بيئة معزولة (supabase start/Docker إن توفر) بتنفيذ VALIDATION.sql.
2. الأسرار (يُعاد إثبات تتبعها أولًا): git rm --cached لما هو متتبع + gitignore كامل (db_url.test.txt) + gitleaks محلي على التاريخ + checklist تدوير تُسلَّم لك (التدوير نفسه خارجي).
3. Dashboard workspace (يُعاد إثبات الفشل بـ pnpm install فعلي): إعادة بناء الحزم الناقصة + lockfile حتى ينجح install/typecheck/build.

## Phase 2 — Security (negative testing إلزامي)
RLS إيجابي/سلبي على بيئة معزولة لكل مسار طالب (enrollments/lessons/todos/notifications/devices/offline entitlements)، فحص SECURITY DEFINER search_path، grants، admin RPCs من authenticated، عزل بذر QA، publication للـ Realtime إن لزم، pinning expiry plan.

## Phase 3 — Functional
مواقع استدعاء Supabash خارج طبقة البيانات (إعادة عدّها فعليًا) → نقل ما يمكن نقله بأمان، تقنين المبرر موثقًا؛ سيناريوهات الخروج القسري؛ drift الـ AGENTS.md يُقنَّن بمواءمة الوثيقة مع الحالة الفعلية أو العكس حسب الأدلة.

## Phase 4 — Release & CI
flutter analyze = صفر تحذيرات، release build فعلي، مراجعة signing/manifest/proguard، تحقق CI workflows مع الشجرة الموحدة، دورة dashboard CI محليًا، dart pub outdated + pnpm audit.

## Phase 5 — RE-SCAN + Final Gate
إعادة مسح كل caller في المستودعين لأي كائن DB عدّلته، إعادة تشغيل الاختبارات، ثم التقرير النهائي `docs/PRODUCTION_READINESS_AUDIT_2026-09.md` بالجداول الإلزامية + إجابات: WHAT IS VERIFIED / FIXED / REMAINS / UNVERIFIED / BLOCKS RELEASE / MUST BE DONE BEFORE GO + **FINAL STATUS: GO/NO-GO/GO WITH CONDITIONS** بالأدلة الفعلية فقط. أي بند يتعذر التحقق منه (تدوير الأسرار، الإنتاج، emulator...) = UNVERIFIED صريح مع طريقة التحقق اليدوي.

قيود معلنة: لا تعديل على القاعدة الحية إطلاقًا؛ كل تحقق DB على بيئة معزولة أو قراءة-فقط؛ تغييرات DB minimal/justified/traceable/testable/reversible مع re-scan للمستودعين بعد كل تغيير.
